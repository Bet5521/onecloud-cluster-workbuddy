## 1. 🔴 CRITICAL

### C-1　面板前端所有 API 请求缺少 Basic-Auth 凭据 → 浏览器内 100% 返回 401

**证据**

后端 `panel/app.py` 的 `require_auth`（第 171–179 行）对**每一个** `/api/*` 路由强制 Basic-Auth：

```
/api/status                          → 受保护
/api/node/<name>/action              → 受保护
/api/service/<node>/<svc>/<action>   → 受保护
/api/exec                            → 受保护
```

前端 `panel/static/js/app.js` 一共 7 处 `fetch()`，**没有一处带上 `Authorization` 头或 `credentials`**：

| 行号 | 调用 | 请求头 |
| --- | --- | --- |
| 9 | `fetch("/api/status")` | 无 |
| 117 | `fetch(\`/api/service/...\`)` | 仅 `Content-Type` |
| 142 | `fetch(\`/api/node/...\`)` | 仅 `Content-Type` |
| 156 | `fetch(...)` 集群操作 | 仅 `Content-Type` |
| 187 | `fetch(...)` 集群操作 | 仅 `Content-Type` |
| 198 | `fetch(...)` 集群操作 | 仅 `Content-Type` |
| 221 | `fetch("/api/exec")` | 仅 `Content-Type` |

**后果**：用浏览器打开面板 → 首次 `GET /api/status` 收到 `401` + `WWW-Authenticate` → 浏览器弹出
原生登录框。用户即使输入了正确的 `PANEL_USER`/`PANEL_PASS`，**浏览器只会把凭据缓存在"该 URL 的
Basic 认证域"里，而 fetch 默认对同源请求是会自动带上已缓存凭据的**——但前提是**用户先在该域上成功
通过过一次挑战**。由于 `app.js` 的 `fetch` 不处理 401、不提示、失败后静默返回，页面呈现的是「空白 +
控制台一堆 401」，用户不知道该在哪登录。面板作为"开箱可用"的交付物是**不可用的**。

**修复建议**（二选一，推荐 A）：

- **A（推荐）** 后端改用会话/Cookie：新增 `GET /login` 表单 → `POST /login` 校验后
  `session["auth"]=True` 并下发 `HttpOnly` cookie；`require_auth` 改为读 session。
  前端无需任何改动，也顺带解决了 C-2（同源 cookie 不受 CORS 的 `origins` 限制）。
- **B（最小改动）** 后端在 401 响应里回一个**极简登录页**（不是 `WWW-Authenticate` 挑战），
  前端 `app.js` 给所有 `fetch` 加 `credentials: "same-origin"`，并在 `refresh()` 里检测 `401`
  时跳转 `/login`。

**测试补强**：`test_panel_frontend_contract` 增加两条断言 ——
① `app.js` 中每个 `fetch(` 语句必须出现在含 `credentials` 的调用里（或全局有 `fetch` 包装函数）；
② `require_auth` 覆盖的路由集合必须与前端实际调用的 URL 前缀集合一致。

### C-2　CORS 只放行 `localhost` 与 `127.0.0.1`，LAN 访问被浏览器拦截

**证据** `panel/app.py:17`：

```python
CORS(app, origins=[f"http://localhost:{os.environ.get('PANEL_PORT','9000')}",
                   "http://127.0.0.1:*"])
```

面板的设计用途就是**从同网段其它机器访问**（`lib-panel-host.sh` 专门做监听地址校验，
`install-service.sh` 有 `--url-host` 参数用于生成访问地址）。但 `origins` 里没有任何 LAN 来源。
从 `http://192.168.1.101:9000` 打开页面（这是**同源**访问，CORS 本不该介入）时，若浏览器把
`Origin` 判定为跨源（例如经 Cloudflare Tunnel 用 `tunnel.yourdomain.com` 访问、或
经 WireGuard 用 `10.8.0.101` 访问），**所有 `fetch` 会被浏览器在发出前拦掉**，控制台报
`has been blocked by CORS policy`。

**注意**：C-1 与 C-2 是**两个独立的阻塞点**，修掉任一个面板都还不能用。

**修复建议**：把 `origins` 改为按运行时实际访问地址动态计算 ——
`lib-panel-host.sh` 已经在维护「本机该网段地址」，让 `app.py` 读同一来源：

```python
_extra = [o for o in os.environ.get("PANEL_CORS_ORIGINS", "").split(",") if o]
_default = [f"http://localhost:{PORT}", f"http://127.0.0.1:{PORT}",
            f"http://{PANEL_URL_HOST}:{PANEL_URL_PORT}"] if url_host else []
CORS(app, origins=_default + _extra)
```

并在 `install-service.sh` 写入 `panel.env` 时**顺带写入 `PANEL_CORS_ORIGINS`**（复用已有的
`--url-host` / `--url-port` 参数，无需新增输入）。若采纳 C-1 的方案 A（cookie 会话），
`origins` 仍需正确，否则浏览器依然不会带上 cookie。

### C-3　数据根存在三套互不兼容的写法，且其中一套的变量从未被赋值

这是本项目**最深的架构一致性问题**。同一个"服务数据在哪"，代码里有三种答案：

| # | 约定 | 出现位置 | 是否正确 |
| --- | --- | --- | --- |
| ① | `<DATA_ROOT>/srv/<完整节点名>` | `deploy.sh:80-81`、`bootstrap.sh` 步骤 14（`safe_install_tree "srv/${NODE_NAME}"`）、`backup.sh` / `restore.sh` / `update-all.sh` / `health-check.sh`（均经 `node_data_root`） | ✅ **设计意图** |
| ② | `/mnt/sd/srv/<完整节点名>` | `panel/app.py:217-220`（`docker_restart` / `docker_up` / `docker_down` / `docker_pull`）、`install-services.sh:184`（`local dir="${DATA_ROOT:-/mnt/sd/srv}/${node}"`） | ❌ 写死 `/mnt/sd`，忽略 `--no-sd` 回退 |
| ③ | `/mnt/sd/<短节点名>/...`（**无 `srv/`**） | `node-wk-edge-01/clash/install-service.sh:11`、`node-wk-iot-02/xiaomusic/install-service.sh:11,14`、`node-wk-iot-02/xiaomusic/config.json:9,10,18`、`node-wk-storage-03/verysync/config.yaml:16,21,24,28`，以及 `clash/install-binary.sh:17`、`xiaomusic/install.sh:21` 的用户提示 | ❌ 与①的目录布局差一层 |

**② 的额外致命细节 —— `DATA_ROOT` 从未被赋值**：

```
$ grep -n DATA_ROOT scripts/install-services.sh
184:    local dir="${DATA_ROOT:-/mnt/sd/srv}/${node}"

$ grep -c lib-nodes scripts/install-services.sh
0

$ awk '/^[A-Za-z_]+=/' scripts/install-services.sh
（只有 4 个颜色变量，无 DATA_ROOT）

$ grep -n DATA_ROOT init/init.sh
（无匹配）

$ grep -rn "install-services.sh" --include=*.sh
init/init.sh:1193   (run_script $SUDO bash "${SCRIPTS_DIR}/install-services.sh" "$target")
init/init.sh:1219   (run_script ... "edge|iot|storage|all-docker")
```

`init.sh` 的 `run_script`（第 298 行）用 `"$@"` 直接继承环境，**不设置 `DATA_ROOT`**；
`install-services.sh` **不 source `lib-nodes.sh`**，也不 import `lib-install-path.sh`。
因此 `${DATA_ROOT:-/mnt/sd/srv}` **恒定展开为 `/mnt/sd/srv/<节点名>`**，
`--no-sd` 场景下这个目录根本不存在 → 原生服务安装全部失败/装到错误位置。

**综合后果**：即使是一台正常的插卡节点，原生服务按③写 `/mnt/sd/<短名>/`，
而部署按①铺 `<DATA_ROOT>/srv/<完整名>/`，两边永远对不上；`--no-sd` 节点上三套全错。

**修复建议**（收敛为一条路径）：

1. `install-services.sh` **改为 source `lib-nodes.sh`**，把 `DATA_ROOT` 换成
   `REMOTE_ROOT="$(resolve_data_root)"`，服务目录统一 `${REMOTE_ROOT}/srv/${NODE_NAME}`；
2. `init.sh` 在调用前显式导出 `DATA_ROOT`（或让 `install-services.sh` 自己探测，更稳）；
3. `panel/app.py` 的 4 个 `docker_*` 命令改为从 `config.json` 读该节点已解析好的远程路径
   （`gen-panel-config.sh` 生成时就把 `data_root` 写进去），不再拼接 `/mnt/sd`；
4. 节点侧原生服务的 11 处 `/mnt/sd/<短名>/` 全部改为**由安装脚本渲染**的占位符
   （安装时用 `sed` 替换真实数据根），systemd 单元进入 `node-*/<svc>/` 模板，不要写死；
5. 补测试：新增一组「数据根单一来源」——扫描全库不得再出现字面量 `/mnt/sd/srv` 与
   `/mnt/sd/<短节点名>`，且任何脚本使用远程路径前必须出现 `node_data_root` 或 `resolve_data_root`。

## 2. 🟠 HIGH

### H-1　`verysync` 在清单与面板中"存在"，但既不在 compose 里，也没有任何安装实现

- `inventory/services.yaml:168` 声明：`node: wk-storage-03`、`container: false`、`port: 19900`。
- `panel/config.json` 一致地把它列为 storage-03 的服务（面板会展示它）。
- `node-wk-storage-03/docker-compose.yml` 里没有它 —— 这是**正确的**（它是原生服务）。
- 但 `scripts/install-services.sh: install_verysync()` **只打印「需要从官网手动下载」**，
  没有下载、没有解压、没有注册 systemd 单元。
- `scripts/health-check.sh` 也不检查它（只检查 syncthing 等容器）。

**后果**：面板显示 `verysync` 为"离线"，用户按文档操作无法让它变成"在线"。
这不是文档瑕疵，是**功能未交付**。

**修复建议**：三选一，必须选一个 ——
（a）补全 `install_verysync()`（下载 armv7 二进制 + 写 systemd 单元 + 端口校验）；
（b）若确实要手动，就在 `services.yaml` 加 `install: manual` 标记，并由
`gen-panel-config.sh` 把它渲染成面板上的「待手动安装」状态（与 H-3 合并做）；
（c）从清单与面板中移除，仅留在文档的"可选扩展"里。
**当前状态（清单说有、装不了、面板显示离线）是最差的一种。**

### H-2　`health-check.sh` 无条件检查 WireGuard，Hub 位置又写死在 edge 角色上

**证据**（`scripts/health-check.sh`）：

| 行 | 内容 | 问题 |
| --- | --- | --- |
| 114 | `WG_HUB_IP="$EDGE_IP"` | 把 Hub 硬绑到 `edge-gateway` 角色 |
| 122 | `check_container "$EDGE_IP" "WireGuard" "wireguard"` | 不判断是否安装了 WireGuard |
| 126 | `check_port "$EDGE_IP" "${NET_WG_PORT}" "WireGuard"` | 同上 |
| 163–173 | `--- WireGuard Mesh ---` 段，`wg show wg0` 失败即 `$FAIL WireGuard Hub 未运行` | 同上 |

**后果**：这是你提出的「选择性安装 WireGuard」需求的**直接阻塞点** ——
不装 WireGuard 的集群跑 `health-check.sh` 会稳定报出 3 个失败项，用户会以为集群坏了。
同样地，若 WireGuard 装在了非 edge 节点（或未来 Hub 换角色），检查结论全错。

**修复建议**：与 H-3 一起做 ——
`health-check.sh` 先读「该节点是否声明安装 WireGuard」，未安装则输出 `SKIP WireGuard (未安装)` 而非 `FAIL`；
Hub IP 改为 `node_ip "$(node_name_by_role edge-gateway)"` 或从 `services.yaml` 的
`wireguard.node` 反查（不要硬编码角色名）。

### H-3　全库没有「已安装 / 未安装」模型 —— 选择性安装需求的根本阻塞

这是你上一条需求（WireGuard 及其它组件选择性安装 + 面板区分显示 + 三种组网模式）的**共同前置条件**，
当前一条都不具备：

| 环节 | 现状 | 需要的改动 |
| --- | --- | --- |
| `inventory/services.yaml` | 没有 `optional` / `enabled` / `installed` 字段，服务被列出来就等于"要有" | 加 `optional: true|false`、`default_enabled: true|false` |
| `inventory/nodes.yaml` | `services:` 是纯列表 | 允许 `services: []`（不含 wireguard）表达"本节点不装 WG" |
| `scripts/gen-panel-config.sh` | 无条件把清单服务全量写进 `config.json` | 渲染 `installed` / `optional` / `enableable` 字段 |
| `panel/config.json` | 无安装态字段 | 同上 |
| `panel/app.py` `collect_all_status()` / `get_service_status()` | 只报 `running`（容器/systemd/pgrep 探测） | 先判 `installed`，未安装直接返回 `installed: false`，**不做 running 探测**（避免误报离线） |
| `panel/templates/index.html` | 拓扑区硬编码文字 "WireGuard Mesh VPN (10.8.0.0/24)" | 按实际模式渲染（WG / LAN / 混合） |
| `panel/static/js/app.js` | 只渲染 在线/离线 与 running/stopped 两种点 | 增加第三态「未安装」（灰色 + 可安装提示） |
| `scripts/health-check.sh` | 无条件检查（见 H-2） | 未安装 → `SKIP` 而非 `FAIL` |
| `pub.kdocs`/ 网段计算 | `wg_subnet` 无条件参与 | 纯 LAN 模式下不参与任何校验 |

**建议的数据流**（一条主线，不分叉）：

```
inventory/services.yaml  {optional, default_enabled}
        │
        ├─→ gen-panel-config.sh ──→ panel/config.json  {installed, optional}
        │                                   │
        │                                   ├─→ app.py: get_service_status() 先判 installed
        │                                   └─→ index.html / app.js: 三态渲染 + 拓扑模式渲染
        │
        └─→ health-check.sh：未安装 → SKIP

inventory/nodes.yaml  network.mode: auto|wireguard|lan|mixed
        └─→ 三种组网模式：wireguard（仅 WG）/ lan（仅直连）/ mixed（两者）
```

## 7. 测试覆盖盲区（值得单独记一笔）

555 项全绿但漏掉 C-1 / C-2 / C-3，说明测试策略有一个共同盲区：
**测试校验"声明与声明一致"（字符串级），不校验"声明与运行时行为一致"（执行级）。**

- 第 15 组校验 `app.js` 里出现的 URL 在 `app.py` 有对应路由 → 通过；
  但没校验"这个 fetch 发出去会不会被 401 / 被 CORS 拦"。
- 第 11 组校验五个来源的服务清单一致 → 通过；
  但没校验"这个服务到底有没有安装实现"（`verysync` 因此漏网）。
- 第 32 组校验数据根一致性 → 通过；
  但它的扫描范围**没有覆盖 `install-services.sh:184` 与节点侧原生服务配置**（只覆盖了
  `bootstrap`/`deploy`/`backup`/`restore`/`health-check` 这几个"预期正确"的脚本）。

建议后续把"取反式断言"作为新增测试的首选形式：
不验证"该有的都有"，而验证"**不该出现的都没出现**"（不得出现字面量 `/mnt/sd/srv`、
不得出现无 `credentials` 的 `fetch`、不得出现 `container: false` 却无安装实现的服务）。
